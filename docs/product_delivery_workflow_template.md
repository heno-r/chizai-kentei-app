# 課金・DB 前提のプロダクト実装フロー

この文書は、単発の制作メモではなく、別案件にも流用できるように抽象化した作業フローです。
対象は、以下の要素を持つ小規模〜中規模のWebサービスを想定します。

- 公開サイト
- ログイン
- 課金
- 権限管理
- DB
- 管理運用

## 1. 企画の固定

最初に決めるもの:

- 誰向けのサービスか
- 無料で触れる範囲
- 有料で解放する範囲
- 何を売るか
  - 買い切り
  - 月額
  - 複数プラン
- どの行動を成功とみなすか
  - 登録
  - 初回利用
  - 購入
  - 継続利用

ここで作るもの:

- 1文で言えるサービス説明
- 無料版と有料版の差分表
- 初期価格案
- 利用者の導線メモ

この段階で大事なこと:

- 機能一覧より、無料と有料の境界を先に決める
- 「誰が何を買うのか」を曖昧にしない

## 2. 情報設計

次に、利用者の動線を整理する。

最低限必要なページ:

- LP
- 無料体験ページ
- ログインページ
- 購入前チェックページ
- 利用規約
- プライバシーポリシー
- 特定商取引法に基づく表記
- 問い合わせページ

最低限必要な利用者状態:

- 未ログイン
- ログイン済み未購入
- 購入手続き中
- 購入済み

この段階で決めること:

- どの状態でどのボタンを見せるか
- ログイン後にどこへ戻すか
- 購入後にどこへ戻すか
- ロック対象をどう見せるか

## 3. システム構成の分離

実装前に、層を分ける。

推奨の分け方:

- 公開フロント
  - LP、無料版、法務ページ、問い合わせフォーム
- secure API
  - ログイン後の状態確認
  - 課金開始
  - webhook 受信
  - 問い合わせ管理用API
- 認証基盤
  - Supabase Auth など
- 決済基盤
  - Stripe など
- DB
  - users
  - orders
  - entitlements
  - content metadata
  - inquiry / support messages
- 非公開コンテンツ置き場
  - R2 など

分ける理由:

- 公開してよいものと秘密情報を混ぜない
- フロントだけ先に公開しやすくする
- 有料コンテンツを public repo に置かない

## 4. データモデル設計

最初に固めるべき基本テーブル:

- users
  - 認証基盤の user id と内部 user id の対応
- orders
  - 購入履歴
- entitlements
  - 何の権利を持つか
- billing_catalog
  - product_code と決済 provider 側 ID の対応
- content_sets
  - 無料セット、有料セット、公開状態
- support_messages
  - 問い合わせ

設計方針:

- 「購入した事実」と「現在持っている権利」を分ける
- UI 判定はできるだけ entitlements から行う
- product / plan / content set を文字列コードで持つ

## 5. 無料版の先行実装

有料版より先に無料版を作る。

先に作る理由:

- 公開サイトの骨格を早く見られる
- 体験品質を先に上げられる
- 課金前に価値が伝わるか確認できる

無料版で先に完成させるもの:

- 問題表示や本体機能の基本
- 主要ページの見た目
- 公開導線
- 問い合わせ導線

ここで見るべきこと:

- 利用者が迷わず使い始められるか
- 有料版へ進みたくなる理由があるか

## 6. ログイン導線の実装

ログインは「後で足す」のではなく、早めに入れる。

最低限必要なこと:

- アカウント作成
- ログイン
- ログアウト
- セッション維持
- 戻り先制御

セキュリティで最低限入れること:

- 失敗時メッセージの曖昧化
- 試行回数制限
- 連続失敗時の一時ブロック
- 可能なら server-side で認証開始を受ける

考え方:

- フロントは入力画面
- 試行制御は secure API 側
- 認証の真実は認証基盤側

## 7. 課金の導線実装

課金はまず sandbox で通し、そのあと live に切り替える。

最小構成:

- 商品 / price の作成
- checkout session 作成
- success / cancel 戻り先
- webhook 受信
- entitlement 付与

この段階で確認すること:

- 決済開始できる
- 支払い完了後に戻れる
- 購入済み状態へ変わる
- 再読み込み後も維持される

## 8. コンテンツ配信の分離

有料コンテンツは公開フロントに埋め込まない。

推奨:

- 無料コンテンツ
  - public API か静的公開
- 有料コンテンツ
  - secure API + 非公開 storage

実装方針:

- 無料セットを土台にする
- 有料セットは追加分として読み込む
- 重複は配信時またはフロントで除外する

## 9. 法務ページと問い合わせ

公開前に最低限そろえるもの:

- 利用規約
- プライバシーポリシー
- 特定商取引法に基づく表記
- 問い合わせフォーム

注意点:

- サービス名と運営者表記を分ける
- 問い合わせ窓口を明確にする
- 返金条件は先に決める
- 施行日を入れる

## 10. 管理運用の実装

公開後に必要なのは、機能より運用導線。

最低限あるとよいもの:

- 本番問い合わせ一覧
- 問い合わせ状態更新
  - new
  - in_progress
  - done
- 日次確認スクリプト
- 返金手順書
- コンテンツ追加手順書

ここで作るべき資料:

- 毎日見るもの
- 返金時の流れ
- 問題追加時の流れ
- 障害時の切り分け

## 11. 本番切替

本番切替前にそろえるもの:

- 公開 repo から secrets が除外されている
- Pages / Hosting の本番URL確定
- Auth redirect URLs 更新
- Payment provider の live keys 設定
- Webhook live endpoint 設定
- secure API 再デプロイ

切替順の例:

1. 公開フロントを本番URLへ
2. secure API の公開URLを確定
3. Auth redirect URLs を更新
4. Payment live keys を反映
5. 本番 checkout を1回通す

## 12. 本番確認

最低限の通し確認:

1. 未ログインで無料版が使える
2. アカウント作成できる
3. ログインできる
4. 購入前チェックへ進める
5. 課金できる
6. 購入後に有料版へ戻る
7. 再読み込み後も権限が維持される
8. ログアウトで無料版に戻る
9. 問い合わせ送信できる
10. 管理側で問い合わせを見られる

## 13. 公開直後の運用

最初の1週間で見るもの:

- 問い合わせ件数
- 購入完了件数
- 決済失敗有無
- ログイン不具合
- 主要URL疎通

この段階では:

- 新機能追加より不具合修正を優先
- 問い合わせ文言や導線を小さく直す
- 課金導線の詰まりを優先で潰す

## 14. 返金時の標準手順

返金運用は最初から決めておく。

推奨フロー:

1. 問い合わせ確認
2. 条件確認
3. Stripe で返金
4. DB の orders / entitlements を更新または削除
5. 再ログイン後に無料状態へ戻る確認
6. 対応履歴を残す

## 15. このフローの使い方

別案件へ流用するときは、最初にこの3点だけ差し替える。

- 売るもの
- 無料 / 有料の境界
- 運用で毎日見るもの

それ以外は、かなり同じ型で回せる。

特に再利用しやすい部分:

- ページ構成
- users / orders / entitlements
- secure API の責務
- 問い合わせ管理
- 本番切替チェックリスト

## 16. ひとことで言うと

この手の案件は、

- 先に無料版で体験を固める
- ログインと課金は secure API で守る
- 有料コンテンツは公開面から分離する
- 公開前より公開後運用を先に用意する

この順で進めると破綻しにくい。
